Self-hosted tunnel · setup guide

up-tunnel / your own ngrok

A small server on your EC2 box gives any local device a public HTTPS URL or a public TCP port — without touching your home router.

public A visitor
  • https://mac.tun.you.com
  • ssh -p 20022 you.com
tcp 443
your ec2 box Tunnel server
  • nginx :443 (TLS)
  • node :8080 http
  • node :8081 control
  • :20000–20099 tcp
wss 443
behind nat Your device
  • python or node agent
  • → 127.0.0.1:3000
  • → 127.0.0.1:22

The device dials out to the server and keeps one WebSocket open. Every tunnelled connection is multiplexed over it, so there is nothing to forward on your router and nothing to open on your firewall.

What you need

Two colours run through this guide: azure marks a command for the remote server, amber marks one for the device you're exposing. Running a step in the wrong place is the most common way this goes sideways.

ThingDetail
An EC2 instanceUbuntu 22.04 or 24.04. A t4g.nano is enough — the server is a byte pump, not a compute load.
An Elastic IPA default public IP changes on stop/start and silently breaks every DNS record below.
A domainAny domain where you can add an A record and a TXT record.
Node.js 20+Installed in step 1. Ubuntu's packaged nodejs is too old.
An agent runtimeOn each device you want to expose: either Python 3.9+ or Node 20+. Two interchangeable agents ship — pick per machine.

This guide uses example.com throughout. Substitute your own domain everywhere it appears.

Version pinning

Node versions are pinned in .nvmrc — run nvm use in server/ or client-node/. The Python client ships a Pipfile with a committed Pipfile.lock, so pipenv install --dev gives you the exact dependency set that was tested.

Install the server

All eight steps run on the EC2 box, except the DNS records in step 0 which you create at your domain registrar. Budget about 30 minutes, most of it waiting for DNS to propagate.

DNS records and the security group

Two A records, both pointing at your Elastic IP:

TypeNameValue
Atunnel.example.comyour Elastic IP
A*.tun.example.comyour Elastic IP

The wildcard is the whole point — once it exists you can invent anything.tun.example.com without ever touching DNS again.

verify from anywhere
dig +short tunnel.example.com
dig +short anything.tun.example.com   # must return the same IP

Then open these inbound ports on the instance's security group:

PortSourceWhy

Narrow that TCP range to what you'll actually use. If SSH on 20022 is the only TCP tunnel you want, open exactly that one port.

4

Create a token per device

on the server
openssl rand -hex 24    # run once per device, keep each output
on the server
sudo tee /etc/uptunnel/tokens.json >/dev/null <<'EOF'
{
  "tokens": [
    {
      "name": "macbook",
      "token": "PASTE_FIRST_SECRET",
      "subdomains": ["mac", "mac-*"],
      "ports": [20000, 20019]
    },
    {
      "name": "raspberrypi",
      "token": "PASTE_SECOND_SECRET",
      "subdomains": ["pi", "pi-*"],
      "ports": [20020, 20039]
    }
  ]
}
EOF
sudo chown uptunnel:uptunnel /etc/uptunnel/tokens.json
sudo chmod 600 /etc/uptunnel/tokens.json
FieldMeaning
nameLabel shown in logs and /status.
tokenThe secret this device presents. At least 16 characters.
subdomainsPatterns this token may claim. * matches any label, pi-* matches a prefix. Omit to allow anything free.
portsInclusive public TCP port range this token may claim.
maxTunnelsCap on simultaneous tunnels. Defaults to 32.

One token per device means you can revoke one without disturbing the others, and the per-token grants stop a compromised Pi from hijacking your laptop's subdomain.

Remember

Tokens are read once, at startup. After editing this file run sudo systemctl restart uptunnel or the new device will be rejected as unauthorized.

5

Configure the server

on the server
sudo tee /etc/uptunnel/uptunnel.env >/dev/null <<'EOF'
CONTROL_HOST=127.0.0.1
CONTROL_PORT=8081
CONTROL_PATH=/control

HTTP_HOST=127.0.0.1
HTTP_PORT=8080
HTTP_DOMAIN=tun.example.com
PUBLIC_SCHEME=https

TCP_BIND_HOST=0.0.0.0
TCP_PORT_MIN=20000
TCP_PORT_MAX=20099
PUBLIC_TCP_HOST=tunnel.example.com

TOKENS_FILE=/etc/uptunnel/tokens.json

ADMIN_HOST=127.0.0.1
ADMIN_PORT=8082

LOG_LEVEL=info
LOG_FORMAT=json
EOF
sudo chown root:uptunnel /etc/uptunnel/uptunnel.env
sudo chmod 640 /etc/uptunnel/uptunnel.env

Two details worth understanding rather than copying blindly:

  • CONTROL_HOST and HTTP_HOST are 127.0.0.1 deliberately — only nginx talks to them, so they're never directly reachable from the internet.
  • TCP_BIND_HOST is 0.0.0.0 because those ports are the public entry points. nginx isn't involved in TCP tunnels at all.

Get a wildcard certificate

Let's Encrypt issues wildcards only over a DNS challenge, so the usual certbot --nginx webroot flow cannot work here.

on the server
sudo apt install -y certbot
sudo certbot certonly --manual --preferred-challenges dns \
  -d tun.example.com -d '*.tun.example.com' -d tunnel.example.com

Certbot prints a TXT value. Create _acme-challenge.tun.example.com with it at your DNS provider, confirm it has propagated, then press Enter:

verify from anywhere
dig +short TXT _acme-challenge.tun.example.com
Renewal

--manual means renewal is manual too, every 90 days. For unattended renewal use your provider's DNS plugin — for Route 53:

on the server
sudo apt install -y python3-certbot-dns-route53
sudo certbot certonly --dns-route53 \

sudo systemctl enable --now certbot.timer

Point nginx at it

on the server
sudo apt install -y nginx
sudo cp /opt/uptunnel/src/deploy/nginx/uptunnel.conf \
        /etc/nginx/sites-available/uptunnel
sudo sed -i 's/example\.com/YOURDOMAIN.com/g' /etc/nginx/sites-available/uptunnel
sudo ln -sf /etc/nginx/sites-available/uptunnel /etc/nginx/sites-enabled/uptunnel
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

Two things in that config are load-bearing:

proxy_read_timeout 7d

An agent's WebSocket sits idle between requests. nginx's default 60 seconds would silently kill every tunnel a minute after it connects.

The Connection: close mapping

already in the shipped config
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

For non-WebSocket requests this sends Connection: close upstream, which stops nginx pooling upstream connections. That matters because the tunnel server reads the Host header once per connection and then pipes raw bytes — a pooled connection carrying a later request for a different subdomain would be misrouted.

Don't

Do not add a keepalive directive to an upstream block for these locations. Requests would start landing on the wrong tunnel.

A config file, for anything you run twice

up.yaml or up.json in the working directory is picked up automatically. All the tunnels come up on one WebSocket.

on your device · up.yaml
server: wss://tunnel.example.com/control

name: macbook

tunnels:
  - name: web
    kind: http

Then just uptunnel. Both agents read this same file, and the JSON form takes the same keys and needs no YAML library at all.

Staying connected

How long a tunnel holds, what breaks it, and what happens next.

How long does one WebSocket last?

Indefinitely. Nothing in the design caps it. A 30-second heartbeat means the connection never sits idle long enough for anything in the path to decide it's dead — the shipped nginx config allows 7d of silence, which the heartbeat keeps you from ever approaching.

What actually breaks connections

CauseNoticed withinRecovery
Home or carrier NAT dropping an idle mappingprevented by the heartbeat—
Laptop sleep, wifi or LTE handover~40sautomatic reconnect
Server restart or redeployimmediatelyautomatic reconnect
Link black-holed with no TCP reset~60sautomatic reconnect

The server pings every HEARTBEAT_MS (30s) and drops an agent that misses a pong. Each agent also pings the server every 20s on its own schedule and reconnects if that goes unanswered — which is what catches a black-holed link, where TCP alone would sit there for minutes.

Reconnection

Exponential backoff from 1s to a 60s ceiling, with ±30% jitter so a fleet of devices doesn't stampede the server after a restart. Every tunnel is re-registered on reconnect, so URLs and ports come back unchanged.

agent log during an outage
02:00:17 WARN  disconnected: connect ECONNREFUSED tunnel.example.com:443
02:00:17 INFO  reconnecting in 2s
02:00:19 INFO  connecting to wss://tunnel.example.com/control
02:00:19 WARN  disconnected: connect ECONNREFUSED
02:00:19 INFO  reconnecting in 4s
02:00:23 INFO  connected as macbook (agent ag_e6c3e726caca, window 256KiB)
02:00:23 INFO  web        https://mac.tun.example.com  ->  127.0.0.1:3000

The backoff resets to 1s only after a session that stayed up for at least 30 seconds. That detail matters: without it, a server that accepts connections and immediately drops them would be retried once a second forever, because every attempt technically succeeded.

What doesn't survive

Connections that were in flight. There is no session resumption, so a download in progress fails and a live SSH session drops. New connections work the moment the tunnel re-registers, typically one to two seconds later.

If you add a load balancer

An ALB or NLB in front of the server brings its own idle timeout — 60s for ALB, 350s for NLB — and will cull connections regardless of your nginx settings. Raise it above HEARTBEAT_MS. Going direct to EC2, as this guide does, has no such limit.

A bad token is the one failure the agent won't retry, since retrying cannot help: authentication failed — unauthorized: token not recognised.

Recipes

All of these run on the device you're exposing.

A local web app

Add --rewrite-host for Vite, webpack or Angular — they reject requests whose Host they don't recognise.

device
uptunnel http 5173 --subdomain demo \
         --rewrite-host

A webhook endpoint

Subdomains are stable across restarts, so you register the URL with Stripe or GitHub once and never again.

device
uptunnel http 4000 --subdomain hooks
# https://hooks.tun.example.com/webhook

SSH into a box behind NAT

Remote commands, scp, sftp, PTYs and VS Code Remote-SSH all work over this.

device
uptunnel tcp 22 --remote-port 20022
from anywhere
ssh -p 20022 pi@tunnel.example.com
scp -P 20022 file pi@tunnel.example.com:~/

A whole LAN, through one port

Expose only SSH, then forward from there. Everything inside stays behind your SSH key.

from anywhere
# router admin on localhost:8080
ssh -p 20022 -L 8080:192.168.1.1:80 \
    pi@tunnel.example.com

# or a SOCKS proxy for the whole LAN
ssh -p 20022 -D 1080 pi@tunnel.example.com

MQTT for IoT devices

The broker stays on your Pi; only the port is public. Turn on broker authentication — anyone can reach it.

device
uptunnel tcp 1883 --remote-port 20083
# mosquitto_pub -h tunnel.example.com \
#   -p 20083 -t sensors/temp -m 21.5

Another machine on your LAN

The agent doesn't have to run on the machine being exposed — handy for a NAS, a printer, or an appliance you can't install anything on.

device
uptunnel http 192.168.1.50:80 --subdomain nas
uptunnel tcp 192.168.1.10:22 --remote-port 20023

WebSockets and streaming need no configuration

The server reads the Host header and then pipes raw bytes, so WebSocket upgrades, Server-Sent Events, long-polling and chunked responses pass through untouched. new WebSocket("wss://demo.tun.example.com/socket") just works, and SSE events arrive as your server emits them rather than buffered to the end.

Running it

Day-to-day operation, and the knobs that matter.

on the server
sudo systemctl restart uptunnel      # after editing tokens or env

Upgrading

on the server
cd /opt/uptunnel/src && sudo -u uptunnel git pull
cd server && sudo -u uptunnel npm ci --omit=dev
sudo -u uptunnel npm install --no-save typescript @types/node @types/ws

Tuning

VariableDefaultRaise it when
STREAM_WINDOW262144High-latency links feel slow. This is the per-stream credit window.
WS_MAX_BUFFERED8388608You have RAM to spare and many concurrent streams per device.
HEARTBEAT_MS30000Mobile or LTE devices are being dropped too eagerly.

STREAM_WINDOW is the main throughput knob. Per-stream throughput is bounded by window ÷ round-trip time — at the 256 KiB default and a 100 ms RTT you top out near 2.5 MB/s. Doubling the window doubles that ceiling, at the cost of memory per stalled stream. Agents pick up the new value when they reconnect.

Why memory stays flat

Every stream is flow-controlled with a credit window in both directions: the sender stops when its credit runs out, and credit only comes back once the receiver's socket has actually accepted the bytes. Measured on a deliberately stalled 150 MB download, the server's resident memory grew by about 15 MB rather than 150 MB.

Troubleshooting

The server logs every rejection with a reason, so journalctl -u uptunnel -f while reproducing is usually the fastest route to an answer.

authentication failed — token not recognised

The token isn't in tokens.json, or the file was edited without a restart. Tokens are read once at startup.

on the server
sudo systemctl restart uptunnel
sudo journalctl -u uptunnel | grep "rejected unknown token"
Connect call failed, or connection refused

Work outwards from the server. If localhost works but nginx doesn't, it's the nginx config; if nginx works locally but not from outside, it's the security group.

on the server
curl -s localhost:8082/healthz
sudo ss -tlnp | grep -E '8080|8081|8082'
curl -sI https://tunnel.example.com/healthz
on your device
dig +short tunnel.example.com
nc -zv tunnel.example.com 443
server rejected WebSocket connection: HTTP 404

The URL is missing the control path. It must be wss://tunnel.example.com/control, not wss://tunnel.example.com.

502 — no device is serving this subdomain

Either no agent is connected, or it claimed a different name. Check what the server actually has:

on the server
curl -s localhost:8082/status | jq '.tunnels[].public'

If the agent is connected, it can't reach your local service. Confirm the target is up on the machine running the agent with curl -v http://127.0.0.1:3000/.

404 — this is not a tunnel hostname

The request's Host doesn't end in HTTP_DOMAIN, or it has more than one label in front of it. a.b.tun.example.com will never route, and a Let's Encrypt wildcard wouldn't cover it either. Check that *.tun.example.com resolves and that HTTP_DOMAIN matches the domain you're browsing.

Tunnels die after about 60 seconds

nginx's proxy_read_timeout is too low for a long-lived WebSocket. The shipped config sets 7d on /control.

on the server
grep -A2 proxy_read_timeout /etc/nginx/sites-enabled/uptunnel
Requests land on the wrong tunnel

Upstream connection pooling is on. The server reads Host once per connection, so a pooled connection carrying a request for a different subdomain gets misrouted. Remove any keepalive directive from the upstream block and make sure the $connection_upgrade map is present.

Invalid Host header, or a blank page from a dev server

Vite, webpack-dev-server and Angular reject unfamiliar Host values. Add --rewrite-host, or rewrite_host: true in the config.

A TCP tunnel registers but connections hang

Almost always the security group. Also confirm TCP_BIND_HOST=0.0.0.0 — with 127.0.0.1 the port only listens on loopback and is unreachable from the internet.

on the server
sudo ss -tlnp | grep 20022
nc -zv tunnel.example.com 20022   # from outside
agent socket congested, pausing all streams

The device's uplink can't keep up with what's being pushed at it. This is the safety valve working — the server refuses to buffer without bound. If it's constant, the device is genuinely saturated.

Reference

Security worth being deliberate about

  • Tokens are bearer secrets in plaintext at both ends. One per device, chmod 600, and keep the control plane on wss:// — over ws:// the token is on the wire.
  • A tunnel is a hole through your NAT. Anyone who guesses the subdomain reaches the service, so don't expose an unauthenticated admin panel and treat the URL as a secret. Put real auth on the service, or keep it behind key-based SSH.
  • subdomains and ports grants limit what a compromised device can claim.
  • The systemd unit runs as a dedicated non-login user with ProtectSystem=strict and no privileged ports.

Known limits

  • No rate limiting or bandwidth caps. A busy tunnel can saturate the box.
  • Tokens are read once at startup. Adding a device needs a restart.
  • One Host per upstream connection is assumed — true for the shipped nginx config, but it breaks if you enable upstream keepalive.
  • In-flight connections don't survive a reconnect. No session resumption, so a download or SSH session in progress dies when the control connection drops.
  • Microcontrollers aren't supported by either client. MicroPython has no websockets library and little RAM, and Node doesn't run there at all. An ESP32 or Pico agent needs a hand-rolled WebSocket framer against the protocol spec — which is why the protocol is small and binary. client/uptunnel/protocol.py is already written in MicroPython-compatible style and lifts across as-is; the rest does not.
  • No web dashboard. /status returns JSON.

What's been verified

Tested end to end with both agents: HTTP GET and POST; 3 MB bodies byte-for-byte intact; 20 concurrent multiplexed transfers; raw TCP with correct half-close; --rewrite-host confirmed against a service that echoes the Host it received; tunnels released on disconnect; reconnect with escalating jittered backoff, re-registering every tunnel. Additionally on the Python agent: a 150 MB body intact, SSE arriving incrementally rather than buffered, and WebSocket upgrades including 512 KiB frames.

For SSH, through both agents: remote command execution, scp of a 20 MB file byte-identical, and PTY allocation. Also verified via the Python agent: sftp and nested ssh -L forwarding back out through the tunnel.

Flow control, measured: a deliberately stalled 150 MB download grew the server's resident memory by about 15 MB rather than 150 MB.

Keeping three implementations honest

The wire format is implemented three times — the Node server, the Node client and the Python client. tests/protocol-vectors.json holds golden byte vectors that both clients assert against, so a protocol change that lands in only one of them fails loudly instead of silently corrupting a tunnel.

on your laptop
cd client-node && npm test        # 7 tests
cd client      && pipenv run test  # 8 tests
